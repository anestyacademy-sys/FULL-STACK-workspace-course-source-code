Build the Kiosk backend, step by step

This guide builds a REST API for a classifieds marketplace from an empty folder. It uses Node.js, Express 5, TypeScript, MongoDB (Mongoose), JWT auth, Zod validation and Multer image uploads.

Every code block is the real code from the backend/ folder. Work through the steps in order and tick each one off as you finish it.

Before you start

The big picture

What the API does

  • Users can create an account and log in. They get back a JWT token that proves who they are.
  • Listings (car, phone, sofa…) can be browsed, searched, filtered and sorted by anyone.
  • Logged-in users can post a listing with a photo, edit it, delete it and see their own listings.

Each layer has one job. If validation fails, the middleware answers right away and the controller never runs. That keeps controllers short and focused.

What you need installed

  • Node.js 22.18 or newer (you have v24). This setup relies on Node's built-in TypeScript support, which is why imports end with .ts. Check with node -v.
  • MongoDB: either MongoDB Community Server running locally, or a free MongoDB Atlas cluster. MongoDB Compass helps you see the data.

The options that matter most here:

  • "strict": true turns on all of TypeScript's safety checks.
  • "noEmit": true: TypeScript only checks the code. Node runs the .ts files directly, so no dist/ folder is built.

  • "verbatimModuleSyntax": true makes you write import type { ... } for things that are only types. Node deletes type imports when it runs the file, so it has to know which imports are types.
Rule to rememberAlways import your own files with the .ts extension, and use import type for interfaces and types. Most "cannot find module" or "does not provide an export named" errors come from breaking this rule.

Shared helpers

Every endpoint answers in the same shape: { success, data, message } on success and { success: false, error, details } on failure. The frontend can then handle all responses the same way.

        data,

    })
}

}

A JWT is a signed string that holds the user's id, email and role. The server signs it with JWT_SECRET, so nobody can fake one without the secret.

import jwt from 'jsonwebtoken';
import { config } from '../config/index.ts';

// payload interface

export interface JwtPayload {
    userId: string;
    email: string;
    role: string;
}


export const generateToken = ( payload: JwtPayload ): string =>{

    return jwt.sign( payload, config.jwtSecret , { expiresIn: config.jwtExpireIn as any } )

}


export const verifyToken = (token: string) : JwtPayload | null  =>{

    try {

        const decoded = jwt.verify(token, config.jwtSecret) as JwtPayload;
        return decoded;

    } catch (error) {
        return null;
    }

}

verifyToken returns null instead of throwing when a token is expired, tampered with or garbage. That makes it easy to use in the auth middleware.

Good to knowA JWT is signed, not encrypted. Anyone can paste it into jwt.io and read the payload, so never put a password or other secret inside it.
Phase 3

Users: register and login

The model describes how a user is stored in MongoDB. The pre('save') hook hashes the password automatically before every save.

import mongoose, { Schema, Document } from "mongoose";
import bcrypt from 'bcrypt';

export interface IUser extends Document {
    name: string;
    email: string;
    phone: string;
    password: string;
    role: 'user' | 'admin';
    createdAt: Date;
    updatedAt: Date;
}

const userSchema = new Schema<IUser>({

        name: {
            type: String,
            required: [true, 'name is required'],
        },
        email: {
            type: String,
            required: [ true, 'email is required' ],
            unique: true
        },
        phone: {
            type: String,
            required: [ true, 'phone is required' ]
        },
        password: {
            type: String,
            required: [true, 'password is required'],
        },
        role: {
            type: String,
            enum: ['user', 'admin'],
            default: 'user'
        }

    },
    {
        timestamps: true
    }

)


// hash the password before saving it
userSchema.pre('save', async function(){

    if(!this.isModified('password')){
        return;
    }

    const salt = await bcrypt.genSalt(10);
    this.password = await bcrypt.hash(this.password, salt);

})


export const User = mongoose.model<IUser>('User', userSchema);
  • IUser is the TypeScript interface. userSchema is the MongoDB shape. Keep them in sync.
  • unique: true on email creates a unique index in MongoDB.
  • timestamps: true adds createdAt and updatedAt automatically.
  • isModified('password') stops the hook from hashing a password that is already hashed, for example when you save a user after changing only their name.
  • The hook uses function(){}, not an arrow function, because it needs this to be the document.

Mongoose protects the database. Zod protects the API: it rejects bad input with clear messages before the controller runs.

import { z } from 'zod';

        .trim(),

    email: z
        .string('email is required')
        .email('invalid email format')
        .toLowerCase()
        .trim(),

    password: z
        .string('password is required')
        .min(6, 'password must be at least 6 characters')

z.infer turns a schema into a TypeScript type, so the controller knows exactly what req.body contains. .toLowerCase() on the email means Rohan@Gmail.com and rohan@gmail.com count as the same account.

A reusable middleware factory. Give it a Zod schema and it returns a middleware that checks req.body or req.params.

import type { Request, Response , NextFunction } from 'express';
import { sendBadRequest } from '../utils/response.ts';


export const validateBody = <T>(schema: any) =>{

    return (req: Request, res: Response, next: NextFunction): void =>{

        const result = schema.safeParse(req.body);

        if(!result.success){
            const errors = formatZodErrors(result.error);
            return sendBadRequest(res, 'validation failed', errors);
        }

        req.body = result.data as T;
        next();

    }

}


export const validateParams = <T>(schema: any) =>{

    return (req: Request, res: Response, next: NextFunction): void =>{

        const result = schema.safeParse(req.params);

        if(!result.success){
            const errors = formatZodErrors(result.error);
            return sendBadRequest(res, 'invalid params', errors);
        }

        req.params = result.data;
        next();

    }

}


const formatZodErrors = (error: any)=>{

    return error.issues.map((err: any)=>{

        return {
            field: err.path.join('.'),
            message: err.message
        }

    })

}

A middleware receives (req, res, next). It either answers (and stops the chain) or calls next() to hand over to the next function. After validation, req.body is replaced with the cleaned data: trimmed, lowercased, and with numbers converted.

A failed validation returns something like this:

{
  "success": false,
  "error": "validation failed",
  "details": [
    { "field": "email", "message": "invalid email format" },
    { "field": "password", "message": "password must be at least 6 characters" }
  ]
}

The actual logic of register and login.

import type { Request, Response } from "express";
import bcrypt from 'bcrypt';

import { User } from '../models/user.models.ts';
import { generateToken } from "../utils/jwt.ts";
import { sendSuccess, sendBadRequest, sendCreated } from "../utils/response.ts";
import type { LoginUserInput, RegisterUserInput } from "../schemas/user.schema.ts";


export const register = async ( req: Request<any, any, RegisterUserInput>, res: Response )=>{

    try {

        const { name, email, phone, password } = req.body;

        // one account per email
        const existingUser = await User.findOne({ email });
        if(existingUser){
            return sendBadRequest(res, 'Email already registered');
        }

        const user = new User({ name, email, phone, password });
        await user.save();

        // log the new user in straight away
        const token = generateToken({
            userId: user._id.toString(),
            email: user.email,
            role: user.role
        })

        sendCreated(res, { user: publicUser(user), token }, 'Account created successfully!');

    } catch (error) {
        sendBadRequest(res, 'error in registration', error);
    }

}


export const login = async ( req: Request<any, any, LoginUserInput>, res: Response )=>{

    try {

        const { email, password } = req.body;

        const user = await User.findOne({ email });
        if(!user){
            return sendBadRequest(res, 'Invalid email or password');
        }

        const comparePassword = await bcrypt.compare(password, user.password);
        if(!comparePassword){
            return sendBadRequest(res, 'Invalid email or password');
        }

        const token = generateToken({
            userId: user._id.toString(),
            email: user.email,
            role: user.role
        })

        sendSuccess(res, { user: publicUser(user), token }, 'Login successful!');

    } catch (error) {
        sendBadRequest(res, 'error in login', error);
    }

}


// never send the password back to the browser
const publicUser = (user: any)=>{

    return {
        _id: user._id,
        name: user.name,
        email: user.email,
        phone: user.phone,
        role: user.role,
        createdAt: user.createdAt
    }

}
  • Register: check the email is free → save the user (the hook hashes the password) → create a token → return the user and the token.
  • Login: find the user by email → compare the typed password with the hash using bcrypt.compare → return a token.
  • Login answers "Invalid email or password" in both failure cases on purpose. That way an attacker cannot find out which emails have accounts.
  • publicUser() picks only safe fields, so the password hash never leaves the server.

Why z.coerce.number()?Creating a listing with a photo sends multipart/form-data, and in a form every field arrives as text, so price is "480000". coerce converts it into the number 480000 before checking it.

A MongoDB id is always 24 characters, so listingIdSchema rejects bad ids early. Without it, Mongoose would throw a CastError.

This middleware protects private routes. It reads the token from the Authorization header, checks it, and attaches the user to req.user.

import type { Request, Response , NextFunction } from 'express';
import { verifyToken } from '../utils/jwt.ts';
import type { JwtPayload } from '../utils/jwt.ts';


export interface AuthRequest extends Request {
    user?: JwtPayload
}


export const authenticate = ( req: AuthRequest, res: Response, next: NextFunction ) : void =>{

    const authHeader = req.headers.authorization;

    if(!authHeader || !authHeader.startsWith('Bearer ') ){
        res.status(401).json({
            success: false,
            error: 'No token provided, please login'
        })
        return;
    }

    // "Bearer xxxxx"  ->  we skip the first 7 characters
    const token = authHeader.substring(7);
    const decoded = verifyToken(token);

    if(!decoded){
        res.status(401).json({
            success: false,
            error: 'Invalid token, please login again'
        })
        return;
    }

    req.user = decoded;
    next();

}

Multer saves the uploaded photo to uploads/listings/ with a unique name, and puts its info in req.file.

import multer from 'multer';
import path from 'path';
import fs from 'fs';


const uploadDir = 'uploads/listings';


if(!fs.existsSync(uploadDir)){
    fs.mkdirSync( uploadDir, { recursive: true } )
}


const storage = multer.diskStorage({

    destination: (req, file, cb)=>{
        cb(null, uploadDir)
    },
    filename: (req, file, cb)=>{
        // Format: listing-1234567890-randomnumber.jpg

        const uniqueSuffixe = Date.now() + '-' + Math.round(Math.random() * 1E9);
        const ext = path.extname( file.originalname );
        const filename = `listing-${uniqueSuffixe}${ext}`;

        cb(null, filename);
    }

})


export const upload = multer({
    storage: storage,
    limits: {
        fileSize: 5 * 1024 * 1024
    }
})
  • The folder is created when the app starts if it does not exist.
  • The file name is listing-<timestamp>-<random>.jpg, so two uploads named photo.jpg never overwrite each other.
  • fileSize: 5 MB rejects huge files.

Multer also fills req.body with the text fields of the form. That is why it must run before validateBody in the route.

Six functions: list, detail, mine, create, edit and delete.

import type { Request, Response } from 'express';

import { Listing } from '../models/listing.models.ts';
import type { AuthRequest } from '../middleware/auth.middleware.ts';
import type { CreateListingInput, EditListingInput, ListingIdInput } from '../schemas/listing.schema.ts';
import { sendSuccess, sendBadRequest, sendCreated, sendNoContent, sendNotFound, sendForbidden } from '../utils/response.ts';


// GET /api/listings/list?cat=Cars&q=swift&sort=price_asc
export const listListings = async ( req: Request, res: Response )=>{

    try {

        const { cat, q, sort } = req.query;

        // 1 - build the filter
        const filter: any = {};

        if(cat && cat !== 'All'){
            filter.category = cat;
        }

        if(q){
            // 'i' means case insensitive
            filter.title = { $regex: q, $options: 'i' };
        }

        // 2 - build the sort
        let sortBy: any = { createdAt: -1 };     // newest first

        if(sort === 'price_asc'){
            sortBy = { price: 1 };
        }
        if(sort === 'price_desc'){
            sortBy = { price: -1 };
        }

        const listings = await Listing.find(filter).sort(sortBy).populate('userId', 'name phone createdAt');

        sendSuccess(res, listings, 'list of listings');

    } catch (error) {
        sendBadRequest(res, 'error in list', error);
    }

}


// GET /api/listings/byid/:id
export const getListingById = async ( req: Request<ListingIdInput>, res: Response )=>{

    try {

        const { id } = req.params;

        // $inc adds 1 to the views counter every time the page is opened
        const listing = await Listing
            .findByIdAndUpdate( id, { $inc: { views: 1 } }, { new: true } )
            .populate('userId', 'name phone createdAt');

        if(!listing){
            return sendNotFound(res, 'listing not found');
        }

        sendSuccess(res, listing, 'listing detail');

    } catch (error) {
        sendBadRequest(res, 'error in detail', error);
    }

}


// GET /api/listings/mine   ( needs a token )
export const getMyListings = async ( req: AuthRequest, res: Response )=>{

    try {

        const listings = await Listing
            .find({ userId: req.user?.userId })
            .sort({ createdAt: -1 })
            .populate('userId', 'name phone createdAt');

        sendSuccess(res, listings, 'my listings');

    } catch (error) {
        sendBadRequest(res, 'error in my listings', error);
    }

}


// POST /api/listings/create   ( needs a token )
export const createListing = async ( req: AuthRequest, res: Response )=>{

    try {

        const body = req.body as CreateListingInput;

        // multer put the uploaded file in req.file
        const imagePath = req.file ? `/uploads/listings/${req.file.filename}` : null;

        const listing = new Listing({
            ...body,
            image: imagePath,
            userId: req.user?.userId
        });

        await listing.save();

        sendCreated(res, listing, 'listing published');

    } catch (error) {
        sendBadRequest(res, 'error in creation', error);
    }

}


// PUT /api/listings/edit/:id   ( needs a token, and you must own the listing )
export const editListing = async ( req: AuthRequest, res: Response )=>{

    try {

        const { id } = req.params;
        const updates = req.body as EditListingInput;

        const listing = await Listing.findById(id);

        if(!listing){
            return sendNotFound(res, 'listing not found');
        }

        if(listing.userId.toString() !== req.user?.userId){
            return sendForbidden(res, 'this listing is not yours');
        }

        const updated = await Listing
            .findByIdAndUpdate( id, updates, { new: true } )
            .populate('userId', 'name phone createdAt');

        sendSuccess(res, updated, 'listing updated');

    } catch (error) {
        sendBadRequest(res, 'error in edit', error);
    }

}


// DELETE /api/listings/delete/:id   ( needs a token, and you must own the listing )
export const deleteListing = async ( req: AuthRequest, res: Response )=>{

    try {

        const { id } = req.params;

        const listing = await Listing.findById(id);

        if(!listing){
            return sendNotFound(res, 'listing not found');
        }

        if(listing.userId.toString() !== req.user?.userId){
            return sendForbidden(res, 'this listing is not yours');
        }

        await Listing.findByIdAndDelete(id);

        sendNoContent(res);

    } catch (error) {
        sendBadRequest(res, 'error in delete', error);
    }

}

Key ideas in this file

  • Dynamic filter: start with an empty object {} (which matches everything) and add conditions only when the query string has them.
  • Search: $regex with 'i' matches "swift" inside "2019 Maruti Swift VXi".
  • Sort: 1 means ascending and -1 means descending.
  • populate: .populate('userId', 'name phone createdAt') replaces the id with the seller's name, phone and join date, and nothing else.
  • Views counter: findByIdAndUpdate with $inc reads the listing and adds 1 to its views in a single database call. { new: true } returns the updated version.
  • Ownership check: before edit or delete, compare listing.userId with the id inside the token. Being logged in is not enough. You must be the owner. .toString() is needed because userId is an ObjectId, not a string.
  • Image path: the database stores /uploads/listings/xxx.jpg. The frontend adds http://localhost:5000 in front to display it.

import { Router } from "express";

import { upload } from "../config/multer.ts";


const router = Router();


// public
router.get('/list', listListings);
router.get('/byid/:id', validateParams(listingIdSchema), getListingById);

// private - a token is required

Phase 7

Going further

The API works, but these are the next things a senior developer would add before putting it online. Each one makes a good exercise.

ImprovementWhyHow
Return 500 for server errorsThe catch blocks currently answer 400 even when the server is at fault, and they send the raw error object to the client.Add a sendServerError(res) helper that returns 500, and log the real error with console.error instead of sending it.
Escape the search textq goes straight into $regex. Characters like ( or .* can break the query or make it slow.q.replace(/[.*+?^${}()|[\]\\]/g, '\\$&') before using it.
Only accept imagesMulter currently saves any file type.Add a fileFilter that accepts only image/jpeg, image/png and image/webp.
Delete the photo with the listingDeleted listings leave their image files on disk.Call fs.unlink on the file in deleteListing.
Allow changing the photo on editThe edit route accepts JSON only.Add upload.single('image') to the edit route and set updates.image when req.file exists.
Stricter id checkThe regex accepts any letter, but Mongo ids use only hexadecimal (0–9, a–f).Use /^[a-f0-9]{24}$/i, or mongoose.isValidObjectId(id).
Require a real JWT secretIf .env is missing, the code falls back to a public default secret.In production, throw an error at startup when JWT_SECRET is not set.
Lock down CORScors() allows every website to call the API.cors({ origin: 'https://your-site.com' })
Pagination/list returns every listing at once.Read ?page=&limit= and use .skip() and .limit().
Security middlewareProtects against common attacks and brute-force logins.helmet and express-rate-limit on /api/users/login.
Cloud image storageLocal disk files are lost on most hosting platforms.Upload to Cloudinary or S3 and store the URL.
